# Mobile (Android) Port Specification

## Problem Statement

Most students live on their phones, and Studdup is desktop-only — that alone blocks the audience it
is built for. Tauri v2 already treats mobile as a build *target* of the same app, so we can ship an
Android build from the same `studdup-core` + React UI, staying fully **local-first** (each device
keeps its own SQLite file). Cloud sync between devices is intentionally deferred to a future paid
tier; this feature is only about running the existing app, well, on a phone.

## Goals

- [ ] The **same monorepo** produces a signed **Android APK** in CI, attached to each GitHub release
      alongside the existing desktop bundles (Windows/macOS/Linux) — one release, all platforms.
- [ ] The app **runs on Android** with data persisted in the platform's app-private storage, using
      the **same schema and forward migrations** as desktop (local-first preserved, no backend).
- [ ] The existing screens are **usable on a phone** (portrait): no horizontal overflow, tap targets
      sized for touch, and every primary flow (see board → open card → estudar → concluir → adiar →
      novo card) reachable one-handed.
- [ ] Desktop behavior and existing desktop users' data are **untouched** by the change.

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
| --- | --- |
| **iOS build** | Needs a Mac runner + paid Apple Developer account + Apple signing. Deferred to a later cycle (AD to be recorded). |
| **Cloud sync / cross-device** | The monetization path (Obsidian-style: local free, sync paid). Requires a backend we are deliberately not building now. |
| **Google Play Store publishing** | Sideloaded signed APK from Releases is the chosen channel this cycle. Play (AAB, dev account, review) is a later decision. |
| **Landscape-optimized layouts** | Portrait is the target for phone/tablet. Landscape must not break (no overflow) but gets no bespoke design. |
| **Biometric / app-lock, background sync, mobile push** | New capabilities, not part of "run the existing app on Android". |
| **Changing any scheduling/domain behavior** | AD-001..AD-016 stay exactly as-is; this is a platform port, not a behavior change. |

## User Stories

### P1: Android build of the app runs from the shared core ⭐ MVP

**User Story**: As a student, I want to install and open Studdup on my Android phone so that I can
plan and run study sessions where I actually am.

**Why P1**: Without the app running on-device, nothing else matters. This is the vertical slice:
the same `studdup-core` + UI, packaged as an Android app that launches.

**Acceptance Criteria**:

1. WHEN the `studdup` crate is built for an Android target THEN it SHALL compile as a library with a
   Tauri **mobile entry point**, and the desktop binary SHALL still build and run unchanged.
2. WHEN the app is launched on Android THEN it SHALL open its database in the platform's
   **app-private storage** (resolved via Tauri's path API), not a relative `data/` fallback.
3. WHEN the app is launched on Android for the first time THEN it SHALL create the schema and run the
   **forward migration** to the current `SCHEMA_VERSION`, identical to desktop.
4. WHEN the app is launched on **desktop** after this change THEN it SHALL resolve the database at the
   **same env-based path as before** (`%APPDATA%/studdup` / `$XDG_DATA_HOME` / `~/.local/share`), so
   existing users' data is untouched.
5. WHEN the database cannot be opened or migrated on Android THEN the app SHALL surface a fatal error
   state rather than silently opening a blank database (preserves the MIG invariant on mobile, where
   `process::exit` is not the right mechanism).

**Independent Test**: `tauri android build` (or `dev`) produces a launchable app; on a device/emulator
it opens, the board renders, and a created card persists across an app restart. Desktop `cargo build`
+ run still opens the pre-existing DB.

### P1: The screens are usable on phone and tablet (portrait) ⭐ MVP

**User Story**: As a student on a phone or tablet, I want the board, card detail, session and "novo
card" to fit and work on a touch screen so that I can actually use the app one-handed on a phone and
comfortably on a tablet.

**Why P1**: A desktop 4-column kanban does not fit a phone. If the UI overflows or targets are
untappable, the Android build is unusable even if it launches. Tablets are a first-class Android form
factor and must be handled, not left to chance.

Three responsive breakpoints (decided AD-017): **phone** `< 640px`, **tablet** `640–1023px`,
**desktop** `≥ 1024px`.

**Acceptance Criteria**:

1. WHEN any primary screen (Quadro, detalhe do card, sessão, Novo Card, Adiar, Histórico) is rendered
   at a phone width (down to ~360px) THEN it SHALL fit within the viewport with **no horizontal page
   overflow**.
2. WHEN the four-column board is rendered on a **phone** THEN the four columns SHALL become **stacked
   full-width sections** in the order Hoje → Amanhã → Próximos → Concluídos, scrolled vertically, none
   clipped off-screen.
3. WHEN the board is rendered on a **tablet** THEN it SHALL use an intermediate multi-column layout
   (2 columns) rather than either the 4-wide desktop grid or the single phone stack.
4. WHEN a user taps a card, an action button, or a modal control on phone/tablet THEN the tap target
   SHALL be **touch-sized** (≥ 44×44px effective) and every modal SHALL be dismissible by touch.
5. WHEN navigation is rendered on a **phone** THEN it SHALL be a **bottom tab bar** (with Novo Card as
   the emphasized action) instead of the left sidebar/rail, so it is thumb-reachable and does not eat
   horizontal space.
6. WHEN navigation is rendered on a **tablet** THEN it SHALL use the existing collapsed icon **rail**
   (AD-009), not the bottom bar.
7. WHEN the viewport is desktop-width THEN the layout SHALL remain the existing desktop layout
   (sidebar + 4-column board) — responsive changes are additive, not a desktop regression.
8. WHEN the navigation is collapsed to the icon **rail** (tablet, or desktop collapsed via Ctrl/⌘+B)
   THEN a **theme (Claro/Escuro) control SHALL remain reachable** from the rail — fixing the current
   bug where the theme toggle disappears entirely when the sidebar collapses. (On phone the theme is
   already reachable via the Configurações screen, so the bottom bar needs no theme button.)

**Independent Test**: Load the UI at 390×844 and 360px (phone), 768×1024 (tablet), and ≥1024px
(desktop); each breakpoint shows its layout (stacked+bottom-bar / 2-col+rail / 4-col+sidebar), no
horizontal scrollbar at any width, all controls tappable; the collapsed rail exposes a working theme
toggle; existing desktop UI tests still pass.

### P1: CI builds and publishes a signed APK with every release ⭐ MVP

**User Story**: As a maintainer, I want each release to automatically include an installable signed
Android APK so that users can download and sideload it the same way they get the desktop installers.

**Why P1**: The chosen distribution channel *is* the release. An unsigned or missing APK means no user
can install the mobile app.

**Acceptance Criteria**:

1. WHEN the release workflow runs THEN it SHALL include an **Android job** that sets up JDK, the
   Android SDK/NDK, and the Rust Android targets, builds the UI, and runs the Tauri Android build.
2. WHEN the Android job builds in release mode THEN it SHALL **sign the APK** using the keystore and
   passwords provided via CI secrets (no plaintext key in the repo).
3. WHEN a release is created THEN the signed APK SHALL be **uploaded as an asset** to that release,
   next to the Windows/macOS/Linux bundles.
4. WHEN the project version is bumped by release-please THEN the Android app version SHALL stay **in
   sync** with the workspace version (same source of truth as the desktop bundles).
5. WHEN the Android job fails THEN it SHALL **not** block or roll back the desktop bundle jobs
   (`fail-fast: false`), so a mobile-only breakage never withholds desktop releases.

**Independent Test**: A tagged release run attaches a `*.apk` asset; the APK installs on a device and
opens; its in-app/manifest version matches the release tag.

---

### P2: Docs cover Android install and build

**User Story**: As a user or contributor, I want the README/SETUP to explain how to install the APK
and how to build the Android app locally so that I'm not stuck.

**Why P2**: Important for adoption and contribution, but the app is functional without it; it can
follow the P1 slice.

**Acceptance Criteria**:

1. WHEN a user reads the README download section THEN it SHALL include the **Android APK** row with
   sideload instructions (enable "install unknown apps", unsigned-publisher caveat).
2. WHEN a contributor reads SETUP.md THEN it SHALL document the Android prerequisites (Android
   Studio/SDK/NDK, JDK, Rust targets) and the `tauri android` dev/build commands.

**Independent Test**: README shows an Android install row; SETUP has an Android build section with the
exact commands.

## Edge Cases

- WHEN the app runs on Android and no legacy `data/srs.db` exists THEN it SHALL simply create a fresh
  DB in app-private storage (the desktop MIG-01 legacy-copy step is desktop-only and SHALL NOT run on
  mobile).
- WHEN the device is offline THEN the app SHALL work fully (it already makes no network calls; this
  must remain true — no analytics/telemetry added).
- WHEN the user uninstalls the Android app THEN the local DB is removed with it (documented; export/
  backup is out of scope this cycle).
- WHEN the UI is rendered at a very narrow width (~320px) THEN it SHALL still avoid horizontal
  overflow (graceful, not pixel-perfect).
- WHEN CI secrets for signing are absent (e.g. a fork's PR) THEN the Android job SHALL fail clearly on
  the signing step (or be skipped for forks) rather than publishing an unsigned/broken artifact.

## Success Criteria

- [ ] A signed `*.apk` is attached to a GitHub release and installs on a real Android phone.
- [ ] On that phone, a user can create a card, open it, run a session, conclude it, and see it move —
      and the card is still there after force-closing and reopening the app.
- [ ] Every primary screen fits a 390px-wide portrait viewport with no horizontal overflow.
- [ ] Existing desktop users open the app after this change and their data is exactly where it was.
- [ ] The desktop release bundles are produced by the same workflow run, unaffected by the Android job.
